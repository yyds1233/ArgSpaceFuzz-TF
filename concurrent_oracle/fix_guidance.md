## 1. 修改目标与总体顺序

本轮重点是提高有效输入覆盖、目标调用重叠、状态型场景覆盖和异常可观测性。采用以下顺序：

1. 建立端到端阳性、阴性验收集，证明异常能沿完整执行链路被发现。
2. 接入 ArgFuzz 已有语料和 PSR 状态，修正只使用前几个 case 的分配方式。
3. 实现逐轮同步、调用前准备参数、低干扰观察及可重放调度扰动。
4. 补充 O5 异常隔离、任务级 O8 进展检查，打通原生故障和 O9 报告路径。
5. 增加 tf.data 完整消费与提前停止场景，再扩展 callback、Variable 和 TSan 定向测试。

不要求一次实现所有 O1—O9，也不以扩大 API 数量或提高 trial 数量代替能力验证。第一阶段先在少量 API 与验收模板上完成闭环，再扩大扫描。

## 4. R01：建立完整检测链路验收集

### 修改目的

在再次全量扫描前，证明检测链路能够从真实子进程观察中识别异常。保留现有比较器单元测试，增加从子进程运行到最终报告的验收。

### 建议新增用例

| 用例  | 构造方式 | 验收要求 |
| --- | --- | --- |
| 正常调用 | 确定性、无共享写入的测试函数 | O2/O3通过，执行数量完整 |
| 输出污染 | 受控测试替身在指定轮返回错误值 | O2报告差异并保存case/轮次 |
| 任务串扰 | 将另一任务的可区分结果返回给当前任务 | O3保存自身与其他任务的对照证据 |
| 输入破坏 | 测试替身修改声明只读的可观察输入 | O4或辅助输入保持检查发现修改 |
| 异常恢复失败 | 预期异常之后，执行器无法继续完成正常任务 | O5保留失败阶段和后续任务状态 |
| 局部停滞 | 一个任务停滞，其他任务继续推进 | O8不被其他任务事件掩盖 |
| 原生崩溃 | 专用子进程受控异常退出 | 记录信号、stderr、事件和运行身份 |
| Sanitizer阳性 | 单独的小型原生测试库包含已知错误 | 能解析报告类型和关键调用栈 |

前四类可先用测试替身验证语义判定。原生错误验收使用独立、明确标注的测试程序，不污染正常扫描环境。

### 验收边界

- 人工注入样例只能证明工具链有效，不计为TensorFlow缺陷。
- 集成测试跳过时，报告明确显示未执行，不能以单元测试通过替代。
- 历史问题回归集另存受影响版本、修复版本、构建方式、触发条件和复现命令。当前版本不复现时，不能直接判定检测无效；尽可能在受影响版本验证。

## 5. R02：接入ArgFuzz语料并保留失败信息

### 输入来源

按以下来源组织case：已有fuzz语料、不同PSR状态的代表性输入、补充变异输入、固定字节冒烟输入。固定8组字节仅用于链路检查，不再承担主要扫描输入。

建议增加显式的输入接口，具体命名由项目现有结构决定：`corpus_dir`、`case_manifest`或直接传入case列表。加载完成后保存输入来源；重复转换同一计划时，不无条件覆盖已有语料和捕获文件。

### case标识与去重

每个case至少记录：

- `case_id`、原始字节哈希与来源路径；
- 源harness哈希、目标API、PSR版本或状态标识；
- shape、dtype及关键普通参数摘要；
- 调用描述摘要、原始对象类型及转换信息；
- 捕获状态、回放状态、串行稳定性；
- 支持的场景与预言机。

按原始字节与实际调用实例两层去重。多个不同字节生成同一参数配置时，不重复计算为参数空间覆盖。初期每API保留20—50个可区分实例作为起始规模，再根据有效性和成本调整；这不是已测得的最优值。

### 捕获失败分流

| 失败类别 | 处理方式 |
| --- | --- |
| 参数构造失败 | 保存阶段、异常和原始字节，进入修复队列 |
| 预期非法输入被拒绝 | 可进入O1/O5，通常不进入普通数值差分 |
| 串行成功、并发异常 | 保存为并发异常候选并触发复核 |
| 未到达目标 | 区分提前返回、分支未命中、包装/解析失败 |
| 参数类型不支持 | 转入对应后端或明确标为能力缺口 |
| 资源不足 | 保存资源状态，单独复核，不直接认定竞态 |

捕获文件应保留`capture_error`、`target_exception`与`construction_exception`等原始信息，不只保留“有无target_calls”。当前资格检查主要检查调用描述是否可重建；仍需将实际回放结果、异常与稳定性接入case状态。

目标异常可能同时在包装器和外层捕获，统计调用次数时不要用异常列表长度直接代替实际调用尝试数。单独维护`attempt_count`、成功数和异常事件标识，避免一次异常重复计数。

### 数据存储

当前超过65,536个元素的普通张量输入会因截断而无法回放，这会限制大规模算子测试。改为元数据JSON加数据文件：数值数组可使用不依赖pickle的数据格式，记录dtype、shape、文件长度和内容哈希；字符串等类型单独编码。加载时验证摘要。

保留原始类型与别名关系。NumPy数组默认应按NumPy数组重建；若允许转换为Tensor，必须记录并限定等价范围。资源对象不能仅保存数值快照后伪装成原对象。

### 验收

- 显式提供超过8个case后，输入源不会被默认值截断。
- 同一语料重复运行可追溯到同一调用描述。
- 一个失败case不阻止其他合格case进入对应测试。
- 大张量可完整重建，文件缺失或摘要不符时报告准备错误。
- 每类捕获失败均可从记录定位到具体阶段。

## 6. R03：case轮换和PSR差异组合

### 当前问题

模板独立调用选择`cases[i % len(cases)]`，线程数固定时，后面的case可能永远不参与并发；共享只读则固定第一个case。增加trial只会继续重复既有选择。

### 修改方式

增加明确的case组合器，至少支持：

1. 同API、同配置、不同元素值；
2. 同API、不同PSR状态或关键参数配置；
3. 同一case共享只读输入；
4. 小规模与较大规模配置组合；
5. 每轮轮换case，覆盖每个合格输入。

第一版先实现轮换和PSR差异组合，不要求枚举所有两两组合。O3使用能够区分的任务参考结果；非单射API的相同输出不能作为串扰证据。

串行基准与并发任务使用相同case身份、输入摘要和调用编号。已获得串行结果但未进入并发的case，单独统计，不能算作完成并发比较。

### 建议统计字段

`eligible_case_count`、`serial_case_count`、`concurrent_case_count`、`compared_case_count`、`case_selection_count`、`psr_state_count`、`configuration_pair_count`、未执行原因。

### 验收

给定8个合格case、2个worker和足够轮数，每个case至少参与一次并发；共享只读模式也轮换所有指定case。新增case组合可以从计划和日志完整还原。

## 7. R04：逐轮执行、同步和低干扰观察

### 执行单元

将当前“线程先同步一次，再自行跑完整组trial”拆为可观察的轮次。保留两种模式：逐轮同步用于提高入口接近程度；持续运行用于自然调度探索。两种模式分别记录，不能混合计算执行强度。

建议最小接口是`prepare_inputs`、`invoke_target`和`describe_results`。先在现有模板内完成职责拆分，无须先重构整个项目。

```python
for round_id in range(rounds):
    selection = select_cases(round_id)
    prepared = prepare_inputs(selection, sharing_policy)
    observations = execute_synchronized_round(
        prepared,
        schedule_seed=schedule_seed,
        round_id=round_id,
    )
    compare_and_record(observations)
```

该代码是接口示意，不是可以直接替换现有模板的实现。

### 同步和失败处理

- 独立输入在屏障前分别重建，不共享可变参数对象。
- 共享只读场景在控制线程构造一次，按声明共享同一对象。
- 每轮在目标调用前同步，记录入口延迟与调度种子。
- 某worker准备失败时，先取消该轮或中止屏障并记录，不让其他worker无限等待。
- 屏障等待错误归为执行器或准备阶段异常，不能直接记为框架死锁。
- 冷启动测试应说明是“首次目标调用”；准备Tensor本身可能已经初始化框架运行时。首次目标调用组与预热组使用独立进程，并明确预热的配置。

### 降低观察干扰

当前事件写入经过全局锁，每次打开文件；输出立即进行NumPy转换、哈希和描述。建议采用每线程事件缓冲、小批次刷盘及有界输出缓存。保留错误发生前后的必要事件，不无限积累大输出。

输出如果引用可变状态，应在定义的观察点快照；不能一律延后读取。纯张量结果可在小批次完成后比较。对大浮点输出采用分块容差比较：哈希相同可以快速判等，哈希不同不能直接判数值错误；缺少完整值时保留INCONCLUSIVE。

### 目标调用重叠指标

记录`round_id`、`task_id`、`call_index`、单调时钟入口/返回时间、结果准备完成时间。统计调用入口时间差、存在多个未返回调用的轮数、完成调用数和case组合数。

这些指标说明调用时间区间重叠，不代表底层C++指令交错覆盖。对于极短调用可采用小批次连续执行和不同参数规模，不强行要求每次都产生可测重叠。

### 验收

用具有受控耗时的测试替身验证逐轮同步确实在每轮发生；参数准备时间不计为目标执行时间；一个worker失败不会造成执行器永久等待；关闭详细日志后仍保留必要故障证据。

## 8. R05：配置必须真正生效，预算与执行规模匹配

### 配置生成

不再仅用YAML列表过滤固定C00—C07。可以保留矩阵名作为预设，但根据显式维度生成受控配置，并保存最终配置与跳过原因。

| 预设  | 外部线程 | 内部线程 | 目的  |
| --- | --- | --- | --- |
| 串行参考 | 1   | 1   | 基本对照 |
| 外部并发 | 2、4、8 | 1   | 隔离外部调用并发 |
| 内部并行 | 1   | 2、4、8 | 检查内部并行实现 |
| 混合并发 | 2或4 | 2或4 | 探索两类并行共同作用 |

不默认生成所有维度的笛卡尔积；限制计划预算，优先保证每种适用场景至少获得一个配置。保存生成、选择、启动、完成各阶段清单。

`inter-op`设置控制独立算子间的并行。单个调用线程执行单个eager算子时，调大inter-op不等于已经产生算子间并行。若需要覆盖该路径，增加有独立分支的图执行模板，并区分首次追踪与稳定执行。

### 预算

拆分`rounds_per_process`、`process_repetitions`、线程数、总时间预算及阶段超时。起始可采用2/4线程、100轮、少量新进程；重点场景再增加到8线程或按时间持续执行。上述为起始建议，不是最优参数结论。

提高轮数后，固定30/60秒进程超时容易把正常慢执行误归类。结合串行参考耗时、总预算、阶段和任务级进展控制停止；Sanitizer构建单独设置预算。

### 环境和身份

- 保存实际可用CPU集合、线程设置和资源配额。第五章多核场景不直接沿用第三、四章单任务1CPU的限制。
- CPU亲和性、入口延迟和受控CPU压力作为独立维度；先建立正常资源下的对照。
- 记录请求配置与实际应用结果，设置失败时不能继续声称该配置已生效。
- `run_id`用于最终报告和oracle结果路径，避免虽然执行目录唯一、最终报告仍被后一次覆盖。
- 缓存标识绑定harness哈希、case摘要、模板版本、框架构建和关键配置。
- 当前`run_harness(run_baseline=...)`及CLI相关参数应核对真实效果：语义差分必须有合格基准；安全/进展测试可以独立执行，但必须明确模式。

### 验收

请求8线程后确实生成并执行8线程计划；默认内部配置不再被静默过滤；运行记录足以重建实际计划；同一计划重复运行的报告互不覆盖。

## 9. R06：O5异常隔离与恢复

### 第一版场景

正常任务A与预期拒绝任务B并发，等待结果后，在同一子进程和同一执行环境中继续提交正常任务C。A/C使用独立输入，B的异常类型先由串行参考确认。

### 观察与判定

- B是否按适用契约拒绝；异常类型、消息和阶段完整保留。
- A是否产生额外异常、错误输出或停滞。
- B结束后，C是否仍能成功完成。
- 执行器是否错误取消无关任务或吞掉异常。

串行成功而并发异常时保存为候选；UNKNOWN契约保留证据，不能强行输出语义VIOLATION。预期异常不等于整个观察不完整，需由场景说明预期状态。

分别记录目标异常、执行器异常和准备错误，不能因为存在任意Python异常就统一丢弃后续结果。

### 验收

正常恢复模板通过；注入恢复失败模板被发现；A/B/C阶段与任务身份可追溯；线程池复用场景确实在同一工作环境中执行。

## 10. R07：任务级O8与阶段进展检查

### 保留并扩展现有watchdog

新版已接入watchdog，不重新实现一套重复监控。扩展监控对象：每个task的阶段、当前调用编号、完成计数、最后有效进展时间；整个进程的准备、运行与退出阶段。

全局日志还在增长不代表每个任务都正常。一个任务持续卡住时，其他任务的事件不能无限刷新它的进展时间。普通日志写入和心跳不自动算作目标任务取得进展。

### 触发后处理

先保存未完成任务清单、最后事件、线程栈、CPU/RSS和时间预算，再终止进程组。保留局部完成的证据，即使无法进行完整O2比较，也生成进展性结果。

区分：准备超时、屏障错误、目标执行无进展、退出停滞、总预算耗尽。超时首先标为候选，通过延长预算、降低线程规模、取消外部压力和加锁对照复核。不要直接把所有TIMEOUT命名为死锁。

### 验收

单任务永久等待、其他任务持续完成的模板仍被识别；正常较慢但持续推进的模板不会因无关阈值误报；事件阶段和退出原因足以定位；线程栈文件存在且与当前run_id关联。

## 11. R08：Sanitizer与O9独立结果路径

### 配置落地

用配置显式指定Sanitizer类型、构建标识、运行库、选项和日志路径，取消依赖某个固定/root路径自动预加载的隐式行为。记录请求状态、检查结果与实际运行环境。

关闭Sanitizer时不擅自加载；开启但不满足条件时明确报告未启用或配置失败。不要仅根据动态库文件存在就声称被测框架已插桩。

### 能力边界

- `-fsanitize=fuzzer-no-link`不能单独证明ASan/TSan能力。
- TSan需要目标代码相应编译插桩与运行库配合；仅预加载运行库不能获得完整检测。
- ASan与TSan采用分别验证的构建，不把它们作为同一个可任意叠加的开关。
- UBSan报告不必然是并发问题；对照串行、加锁和重复执行判断并发关联。
- 部分第三方库未插桩时记录覆盖边界，不声称已覆盖所有内部竞争。

### 报告与归并

解析报告类型、访问位置、相关线程、栈、进程退出码和原始日志路径。Sanitizer报告即使不导致进程退出也必须被采集；原生崩溃即使没有观察JSON也必须有独立结果。

O9不只绑定非法输入场景。合法输入的独立并发、tf.data和资源场景也应启用原生错误观察。扫描结束按规范化栈和故障类型归并候选，不按运行次数当作独立缺陷数。

### 验收与推进

先用现有可用构建打通ASan/原生崩溃路径，再单独验证TSan构建和小型数据竞争阳性样例。完成配置检查、报告解析和预算评估之后，才对重点TensorFlow场景启用TSan扫描。

## 12. R09：tf.data配方后端与O6

### 不直接序列化运行时对象

保留现有纯算子冻结参数回放路径，为Dataset、callback和Variable增加配方后端。配方保存构造模板、参数、种子和场景步骤；在各子进程内创建真实对象。

建议后端接口：

```python
prepare(case_spec)        # 构造当前进程内的输入与资源
run_step(context, task)   # 执行约定操作
observe(context)         # 获取输出、状态和进展
cleanup(context)         # 按场景语义结束和释放
```

先实现少量固定模板，避免把通用对象序列化作为前置工程。当前捕获结构虽然能保存多个目标调用，但属于冻结参数列表，不能据此声称保存了返回值依赖、共享资源身份和完整状态序列。

### 首批三个模板

| 模板  | 构造与执行 | 适用检查 |
| --- | --- | --- |
| 并行map完整消费 | 有限数据源，每元素带唯一ID；改变并行度和工作负载 | 数量、ID多重集合、值与ID关联 |
| interleave完整消费 | 多个带来源ID与局部ID的有限子数据集 | 来源关联、遗漏、重复与值完整性 |
| 提前停止并继续工作 | 消费部分元素后结束本轮，再创建并消费新管线 | 后续进展、后台异常、退出行为 |

使用有限、可计算预期结果的数据源。第一版先各任务独立iterator，再研究有明确契约支持的共享iterator操作。

### 顺序和确定性

允许乱序时比较元素多重集合，不按返回顺序判错。元素ID与结果关联分别检查，避免仅比较总数掩盖重复和丢失。

全局确定性开关可能使部分带状态操作的map/interleave串行执行并影响预取。划分两种模式：语义差分模式使用确定性输入与适用比较；生命周期和进展模式保留目标并行机制，以完整性、恢复、退出和原生错误为主要检查。

### 提前停止的边界

`take(k)`检查返回的k个结果，不要求后台callback恰好执行k次。预取可提前执行额外工作。不能要求释放Python引用后资源立即销毁，也不假定所有iterator具有统一公开close接口。结束方式和期望应按具体模板定义。

### 验收

完整消费模板在正常实现上通过；人为丢失、重复、错配元素能被识别；允许乱序时不误报；提前停止后正常任务能够继续执行；卡住或退出异常能进入O8/O9证据路径。

## 13. R10：callback/generator生命周期与O7

在tf.data配方后端上增加：正常callback、在指定元素抛出预期异常的callback、有限generator、提前停止后创建新管线。

记录callback进入/退出、元素ID、异常、管线身份与后续任务状态。Python callback受GIL等因素影响，不能根据设置的并行度推断Python回调体必然并行；需要结合实际观察。

不要人为并发访问同一个未承诺线程安全的Python generator，然后把其拒绝重入当作TensorFlow缺陷。不要根据垃圾回收发生时间或多执行了几个预取callback直接判错。

验收重点是已定义场景中的结果完整性、异常传播、后续恢复、无进展与原生安全，而不是笼统要求“立即释放所有资源”。

## 14. R11：Variable资源场景与操作级契约

### 扩展顺序

1. 每线程独立Variable：检查资源隔离。
2. 共享Variable只读：检查无写入条件下的一致性与进展。
3. 共享Variable更新：核实具体操作的并发契约后设置状态预期。
4. 创建、使用和结束资源：按支持的生命周期操作定义场景。

资源配方保存初值、dtype、shape、别名关系与操作序列。独立资源必须分别创建；共享资源在同一进程内创建一次，不能通过复制数值代替共享对象。

### 判定边界

`v.assign(v + 1)`包含读取、计算和写入多个步骤，未经契约确认不能要求最终值必定等于总调用次数。即使采用`assign_add`，也应核实当前操作和资源类型支持的性质。

优先检查有依据的最终状态、范围和安全性，不默认每次并发读取都具有某个固定串行顺序。契约不足时记录候选，不强行判VIOLATION。

不主动在仍被使用时销毁资源，除非该操作组合有明确支持和对应期望；否则测试程序本身可能引入未定义或不受支持的行为。

## 15. R12：候选复核、报告与实验口径

### 候选复核

发现差异、异常、停滞或Sanitizer报告后，保存完整配方、语料、调度种子、框架构建、配置和原始事件。随后进行适用的交叉复核：

1. 同配置在多个新进程重复执行，报告触发次数/实际执行次数。
2. 串行与多线程加锁对照。
3. 减少线程数、缩短调用序列、缩减输入规模。
4. 首次目标调用与预热后调用对照。
5. 去除外部压力、调整预算，排除单纯资源不足。

同一进程内的100轮调用不能写成100次独立进程复现。加锁后消失是关联证据，仍需结合资源和执行器状态分析。

### 汇总口径

建议分开保存三类状态：执行状态、覆盖完整性、语义/安全发现。CLEAN必须附带实际测试范围；WARNING不能自动当作无缺陷；没有可运行场景的API与已经完成比较的API分开统计。

| 指标组 | 至少报告的字段 |
| --- | --- |
| 计划覆盖 | 生成、选中、启动、完成数量及跳过原因 |
| 输入覆盖 | 合格、串行执行、并发参与、完成比较的不同case数 |
| 配置覆盖 | PSR状态数、配置组合数、线程配置、重复进程数 |
| 执行强度 | 轮数、实际调用数、调用重叠轮数和入口时间差 |
| 检测结果 | 各预言机候选、原生错误、复核触发率、归并后候选数 |
| 成本  | 测试执行、观察采集和候选复核的耗时 |

### 第五章可开展的组件实验

| 对照  | 回答的问题 |
| --- | --- |
| 固定字节 vs ArgFuzz语料/PSR代表性case | 能否提高合格输入和参数状态覆盖 |
| 首N个case vs 轮换/PSR差异组合 | 是否扩大实际参与并发的配置范围 |
| 仅首次屏障 vs 逐轮同步 | 是否增加目标调用重叠和有效触发机会 |
| O2/O3 vs 增加O5/O8/O9 | 新增检测能力发现哪些不同类型的异常 |
| 纯算子回放 vs 加入tf.data配方 | 是否覆盖原先遗漏的状态与生命周期行为 |

比较时冻结case池、框架构建和明确预算。压力参数、线程数和观察成本均记录。人工故障验收、历史问题复现和新缺陷发现分别报告，避免混在同一缺陷数量中。
